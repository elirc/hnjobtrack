# Concepts: CRUD under retries

CRUD correctness is about the whole lifecycle, not just a successful insert. Create establishes a thread checkpoint. Read discovers that checkpoint and reads the remote children. Update marks the thread as parsing; duplicate-ignore leaves an existing child, including raw and parsed fields, untouched. Delete is represented by database cascade when a thread is removed; this change does not invent a new deletion policy. The boundary between these operations is where partial failure lives.

Idempotency means the same logical request has the same durable result when repeated. In this project the logical child key is `(thread_id, hn_comment_id)`, not a random UUID. An ordinary insert would duplicate listings after a retry. An upsert with `ignore_duplicates` plus a database unique constraint turns “retry” into “create if absent, preserve if present.” The constraint is important because two workers can race between a read and a write; the application cannot serialize that race reliably on its own.

Authorization and data boundaries still matter even in a scraper. The admin route guards who can start the pipeline. The importer accepts only comments whose `parent_id` equals the requested story, so nested discussion cannot become a job listing. Empty text is rejected before persistence. The importer does not call notifications or an external model, which keeps its transaction-sized responsibility clear. When debugging a CRUD bug, name the identity key, the source of truth, the retry point, and the invariant that must hold after every interruption.

The tradeoff is deliberate. A full replacement could remove stale comments, but it would also create a larger failure window and might disturb parsed fields. Duplicate-ignore favors monotonic repair: missing children are added while existing rows remain unchanged. If product requirements later demand refreshing raw text or deleting comments removed upstream, that is a separate reconciliation policy requiring explicit evidence and tests.

The Supabase Python contract supports `on_conflict`, `ignore_duplicates`, and `default_to_null`; the staged call uses all three so the composite key is explicit, existing parsed rows are preserved, and omitted database defaults remain available. See the [Supabase upsert reference](https://supabase.com/docs/reference/python/upsert) and [PostgREST conflict-target reference](https://docs.postgrest.org/en/v14/references/api/tables_views.html). These links document the intended API, not a live database result.
