# Testing and debugging

The focused test module uses only the standard library. `FakeDB` records table, payload, and conflict target; `FakeQuery` models the fluent methods used by the importer. One test supplies an existing thread context and verifies that the importer writes the comment using the composite conflict key. A second test supplies a top-level comment, a nested comment, and empty text, then asserts that only the valid row is written. These tests target the changed contract rather than reproducing the entire web stack.

To debug a failure, first classify it. If the call list has no `job_listings` write, inspect the retry branch and whether the HTTP response produced hits. If the write has duplicates, inspect the conflict target and the SQL constraint. If nested comments appear, inspect the integer comparison against the requested story id. If parsed values disappear, inspect whether the upsert payload contains parser-owned columns. Record the observed call sequence before changing code; call traces are more useful than a vague “scrape failed.”

Run `python -X utf8 -m unittest discover -s tests -p 'test_scraper_resume.py' -v` from `backend`. This does not prove Algolia pagination, Supabase semantics, or parser correctness. It proves the pure import boundary’s filtering and conflict intent. A stronger follow-up would run against an isolated database with the actual unique index and simulate a process interruption between batches.

For a debugging lab, add a recording fake that raises on the second upsert. Then assert the first batch remains observable and explain why a later retry should resend it safely. This is a better exercise than mocking every HTTP detail because it isolates the durability boundary. Keep test names phrased as contracts, such as “retry imports missing comments,” so failures teach the next maintainer what behavior matters.

The expanded recovery suite invokes the real scrape entry point, including pagination and a 501-row import interrupted at the second batch. It verifies recovery after an HTTP failure following parent creation and preserves seeded parsed fields under the explicitly modeled duplicate-ignore contract. Run both suites from backend with `python -m unittest discover -s tests -p "test_scraper*.py" -v`. The database double records and models the requested API contract; it cannot certify SQL isolation or migration execution.
