# Testing and debugging

Both test modules use only the standard library; they stub `httpx` and `app.core.supabase` before importing the scraper, so no `pip install` is needed. In `backend/tests/test_scraper_resume.py`, `FakeDB` records table, payload, and conflict options; `FakeQuery` models the fluent methods. Its three tests: a `pending` thread is refetched and upserted with `("thread_id,hn_comment_id", True, False)` (lines 70-90); a `done` thread produces no `job_listings` write (lines 92-103); and `_import_comments` keeps only the top-level, nonempty comment out of three (lines 105-113). These tests target the changed contract rather than reproducing the entire web stack.

To debug a failure, first classify it. If the call list has no `job_listings` write, inspect the retry branch and whether the HTTP response produced hits. If the write has duplicates, inspect the conflict target and the SQL constraint. If nested comments appear, inspect the integer comparison against the requested story id. If parsed values disappear, inspect whether the upsert payload contains parser-owned columns. Record the observed call sequence before changing code; call traces are more useful than a vague “scrape failed.”

Run `python -X utf8 -m unittest discover -s tests -p 'test_scraper_resume.py' -v` from `backend`. This does not prove Algolia pagination, Supabase semantics, or parser correctness. It proves the pure import boundary’s filtering and conflict intent. A stronger follow-up would run against an isolated database with the actual unique index and simulate a process interruption between batches.

The recovery suite (`backend/tests/test_scraper_recovery.py`) already contains the "raise on the second upsert" fake: `Database.fail_batch` makes `Query.execute` raise on the Nth upsert (lines 35-36), and its `rows` dict uses `setdefault` keyed on `(thread_id, hn_comment_id)` (line 39) to model `ignore_duplicates`. Read `test_partial_batch_retry_preserves_parsed_fields` (lines 106-121): it fails batch 2 of a 501-row import, checks 500 rows survive with status still `pending`, retries, and asserts the batch sizes were `[500, 1, 500, 1]` with the seeded row unchanged. Keep test names phrased as contracts, such as "retry imports missing comments," so failures teach the next maintainer what behavior matters.

The recovery suite drives the real `scrape_latest_thread` entry point, covering pagination, recovery after an HTTP failure following parent creation, the `done` early return, filtering via a thread in `error` status, and the no-story path (six tests). Run both suites from `backend` with `python -X utf8 -m unittest discover -s tests -p "test_scraper*.py" -v` (9 tests, re-run OK on 2026-10-06 with Python 3.13). The database double models the requested API contract; it cannot certify SQL isolation or migration execution. Note that the seeded row in the parsed-field test uses `parsed_data`/`is_parsed` keys, which are not columns in `supabase/schema.sql` (the real parsed columns are `company`, `skills`, `parsed_at`, etc.); the fake does not care, but a real-database version of the test must use real columns.
